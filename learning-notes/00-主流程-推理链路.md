## 1. 项目分层（心智地图）

llama.cpp 是一个「洋葱」：从用户命令到 GPU 算子，一共五层。每层只关心本层的事，层与层之间靠明确的数据结构对接。

```
┌─────────────────────────────────────────────────────────────┐
│ 工具层   tools/server, tools/cli, examples/                  │
│          入口：llama-cli / llama-server                      │
│          职责：命令行参数、HTTP/终端 IO、任务调度           │
├─────────────────────────────────────────────────────────────┤
│ 公共层   common/                                            │
│          职责：参数解析、采样封装、对话模板、grammar         │
├─────────────────────────────────────────────────────────────┤
│ 核心层   src/ (libllama)                                    │
│          职责：模型加载、上下文、构图、KV cache、采样器     │
├─────────────────────────────────────────────────────────────┤
│ 张量层   ggml/                                              │
│          职责：tensor 计算图 + 各后端 (CPU/CUDA/Metal/Vulkan)│
├─────────────────────────────────────────────────────────────┤
│ 文件层   gguf-py/ + convert_hf_to_gguf.py                   │
│          职责：HF 权重 -> GGUF 文件格式（运行时不走这里）   │
└─────────────────────────────────────────────────────────────┘
```

每层各自有什么「不外泄」的本分：

| 层 | 不应该知道的事 | 必须知道的事 |
|----|----------------|--------------|
| 工具层 | 后端是 CPU 还是 CUDA | 用户传了哪些参数、prompt 是什么 |
| 公共层 | 模型有几层 transformer | 采样参数、grammar 字符串 |
| 核心层 | 用户在终端还是 HTTP | batch 里的 token/位置、KV cache 形状 |
| 张量层 | 这是什么模型 | tensor 的 shape、op 依赖关系 |

### 心智地图练习：「加一个新命令行参数 `--foo` 要动哪些层？」

把这张图反过来用，就理解了分层意义。假设你想加一个 `--foo 42` 参数，让生成时每 42 个 token 打一次 checkpoint。改动从上往下流：

1. **公共层 `common/arg.cpp`**：在 `common_params_parser_init` 注册一个 `--foo` 选项，回调把值写进 `params.foo`。**只动这里**就能让 `--foo` 出现在 `--help` 里。
2. **公共层 `common/common.h`**：给 `common_params` 加字段 `int32_t foo = 0;`。
3. **工具层 `tools/server/server-context.cpp`**：在 `load_model()`（行 998）把 `params.foo` 拷到 `params_base`；在 `pre_decode()`（行 2831）的 checkpoint 判定里用它。
4. **核心层、张量层**：通常**不动**。`--foo` 不改前向计算，只是改了「何时存 KV 快照」，所以核心层接口完全不变。

这一练习告诉你：**核心层 / 张量层是稳定的接口边界**。上层花样再多，到底层的都是 `llama_decode(ctx, batch)`。

> **最重要的一条架构认知**：现代 llama.cpp 里 `llama-cli` 只是 `llama-server` 的**薄客户端**。真正的推理引擎集中在 `tools/server/server-context.cpp`。不要从旧版 `examples/` 出发——`tools/cli/cli.cpp` 第 8–10 行直接 `#include "server-context.h"`，CLI 内嵌一个 `server_context ctx_server` 复用整套引擎。`examples/` 已不是主路。

### 一个循环的收官

每生成一个 token，`pre_decode() -> decode() -> post_decode()` 循环往复，直到触发停止条件
（EOS token / 生成长度 / 上下文满 / 客户端中断）。`process_token()` 返回 `false` 即代表停止。

## 3. 用一个具体例子走一遍：`-p "1+1=?"`

讲清「函数输入输出具体化」最有效的办法是把抽象的 batch 字段换算成数字。下面走一遍生成第一个 token 的全过程。**为可读性，假设词表很小、token id 是编的**，但流程与真实代码一致。

### 3.1 终端命令

```
llama-cli -m tiny.gguf -p "1+1=?" -n 4 --no-conversation
```

### 3.2 命令行解析 `common_params_parse()` (`common/arg.cpp:930`)

`argv` 被解析后填入 `common_params params`：
```
params.model.path      = "tiny.gguf"
params.prompt          = "1+1=?"
params.n_predict       = 4
params.sampling.temp   = 0.8     // 默认值
params.sampling.top_k  = 40
...
```

### 3.3 模型加载 `load_model()` (`server-context.cpp:998`)

`llama_model_load_from_file()` 解析 GGUF 头，拿到 `hparams.n_layer=16, n_embd=4096, n_vocab=32000` 等。
`llama_init_from_model()` (`src/llama-context.cpp:3490`) 分配：
- **KV cache**：`memory.reset(model.create_memory(...))` (`src/llama-context.cpp:333`、`src/llama-model.cpp:2003`)，按 `n_ctx × n_seq_max × type_k/type_v` 切分。
- **输出 buffer**：`output_reserve(params.n_seq_max)` (`src/llama-context.cpp:313, 2062`)，为 logits 申请 `n_vocab × n_outputs_max` 个 float。
- **scheduler scratch**：`sched_reserve()` (`src/llama-context.cpp:439`)，跑空图测峰值（见 §6）。

### 3.4 tokenize `tokenize_cli_input()` (`server-context.cpp:2248`)

CLI 路径下 `process_single_task()`（行 2353）发现 `task.cli == true`，先调 `tokenize_cli_input()`：
```
输入: cli_prompt = "1+1=?"
输出: task.tokens = [29902, 29900, 29902, 28760, 29973]  // 假设的 id
                          ↑'1'    ↑'+'    ↑'1'   ↑'='    ↑'?'
```

### 3.5 prompt 阶段：第一次 `pre_decode()`

`launch_slot_with_task()` (`server-context.cpp:1718`) 把 slot 状态置为 `SLOT_STATE_PROCESSING_PROMPT`，并 `common_sampler_init(model, params.sampling)` (`server-context.cpp:1794`、`common/sampling.cpp:187`) 构造采样链。

`pre_decode()` 内的 while 循环（行 3443）把 5 个 prompt token 装进 batch：
```
batch.n_tokens = 5
batch.token    = [29902, 29900, 29902, 28760, 29973]
batch.pos      = [    0,     1,     2,     3,     4]
batch.seq_id[i]= [0]                 // 全部属于 sequence 0
batch.logits   = [   0,     0,     0,     0,     1]  // 只要末 token 的 logits
```
**为什么 prompt 一次喂 5 个？** 见 §4.3。简言之：prompt 各 token 之间没有数据依赖，可以并行算；而生成阶段每个 token 都依赖前一个的采样结果，只能串行。

### 3.6 `decode()` → `llama_decode()` → 前向

`decode()` (`server-context.cpp:3578`) 把 batch 切成 `n_batch` 大小的子段循环喂给 `llama_decode()`（行 3612）。本例 5 个 token 远小于 `n_batch`，所以只调一次：

```
llama_decode(ctx_tgt, batch_view)  // src/llama-context.cpp:4054
  -> llama_context::decode(batch_inp)  // 行 1680
       1. balloc->init(batch_inp, ...)   // 行 1731：整理 token、pos、输出掩码
       2. sched_reserve()                // 行 1761：必要时重跑空图调大小
       3. memory->init_batch(...)        // 行 1771：KV cache 给本 batch 划槽
       4. model.build_graph(params)      // src/llama-model.cpp:2234：构图
       5. graph_compute(gf, ...)         // 行 2421：调度后端执行
            └─ ggml_backend_sched_graph_compute_async(sched, gf)  // 行 2440
       产出: logits[5个位置中只有 pos=4 这一行有效]
              形状 = [1, n_vocab=32000] 的 float 行
```

logits 的物理形状是 `output_reserve()` 决定的（`src/llama-context.cpp:2087`：`logits.size = n_vocab * n_outputs_max`），只有 `batch.logits[i]==1` 的位置才会真正写。

### 3.7 `post_decode()` 采样

`post_decode()` (`server-context.cpp:3702`) 遍历每个 slot，对它的 `i_batch` 索引执行：
```
tok_idx = slot.i_batch - off = 4 - 0 = 4
id = common_sampler_sample(slot.smpl.get(), ctx_tgt, tok_idx=4)
     // common/sampling.cpp:540
     //   1. llama_synchronize(ctx)         // 等 GPU 完事
     //   2. gsmpl->set_logits(ctx, 4)      // 把 logits 第 4 行装进 cur_p
     //   3. llama_sampler_apply(chain, &cur_p)  // 依次走 top_k/top_p/temp/...
     //   产出 id = 29902 (假设是 "2")
common_sampler_accept(slot.smpl.get(), id=29902, is_generated=true)
     // common/sampling.cpp:444
     //   把 29902 喂给链里每个 sampler 的 accept()，更新内部状态
process_token(result, slot)   // server-context.cpp:1839
     //   检查 EOS、停止词、预算；这里继续
send_partial_response(slot, result, false)  // server-context.cpp:2061
     //   把 "2" 通过 queue_results 推回客户端
```

### 3.8 生成阶段：第 2~4 个 token

下一个 `update_slots()` 来时，slot 状态已变成 `SLOT_STATE_GENERATING`，`pre_decode()` 只装 **1 个 token** 进 batch：
```
batch.n_tokens = 1
batch.token    = [29902]   // 上一步采到的 "2"
batch.pos      = [    5]
batch.logits   = [    1]
```
然后 `decode() -> post_decode()` 再走一遍，得到下一个 token。循环 4 次后 `n_decoded == n_predict`，`process_token()` 返回 `false`，`send_final_response()` 收尾。

> 注意：prompt 阶段一次喂 N 个，生成阶段一次喂 1 个——**用的是同一个 `llama_decode()`**。差异只在 batch 的大小和位置数组。这就是 batch API 的设计目标：用一个接口覆盖两种工作模式。

## 4. `llama_batch` 结构详解

batch 是工具层与核心层之间的「集装箱」。看懂它的字段就懂了一半推理工程。

### 4.1 字段定义（`include/llama.h:240`）

```c
typedef struct llama_batch {
    int32_t n_tokens;        // 这一装 batch 里装几个 token

    llama_token  *  token;   // 输入 token id 数组（与 embd 二选一）
    float        *  embd;    // 或直接输入 embedding（多模态、MTP 走这条）
    llama_pos    *  pos;     // 每个 token 的位置（用于 RoPE、KV cache 索引）
    int32_t      *  n_seq_id;   // 第 i 个 token 属于几条 sequence
    llama_seq_id ** seq_id;  // 每个 token 的 sequence id 列表
    int8_t       *  logits;  // 第 i 个 token 是否需要输出 logits（0/1）
} llama_batch;
```

### 4.2 三个易混字段的含义

- **`pos`**：Transformer 里的「时间步」下标。同一个 sequence 内必须递增；不同 sequence 之间互不干扰。
  例：3 个 token 的 prompt batch，`pos = [0, 1, 2]`。
- **`seq_id`**：KV cache 是按 sequence 隔离的「档案柜」。`seq_id[i]` 告诉系统「这条 token 的 K/V 写哪个抽屉」。多 slot 并行时，slot 0 的 token `seq_id=[[0]]`，slot 1 的 `seq_id=[[1]]`。
- **`logits`**：算 logits 是有代价的（vocab 可能十几万）。`logits[i]==0` 表示「不要输出这个位置的 logits」——prompt 阶段只有最后一个 token 需要 logits，其余设 0 省一大块输出 buffer。

### 4.3 为什么 prompt 阶段一次喂全部、生成阶段一次喂 1 个

| 维度 | Prompt 阶段 | 生成阶段 |
|------|-------------|----------|
| token 数 | 几十到几千 | 1 |
| token 间依赖 | **无**（已知输入） | **强**（下一个依赖上一个采样结果） |
| KV cache 写入 | 全部写 | 增量写 1 行 |
| logits 需要 | 仅末位 | 那一位 |
| 性能特征 | 并行度高，受 `n_ubatch` 限制 | 串行，受单步延迟限制 |

`n_batch`（`include/llama.h:338`，逻辑上限）和 `n_ubatch`（行 339，物理上限）就是为这两种模式准备的。prompt 阶段一次性把 token 装满 `n_batch`，核心层内部再按 `n_ubatch` 切成 micro-batch 喂给后端（见 `llama_context::decode` 的 `balloc` 与 `process_ubatch`，`src/llama-context.h:137`）。生成阶段 batch 只有 1 个 token，远小于 `n_ubatch`，等于白浪费并行度——这是自回归生成的固有代价。

### 4.4 简化代码：服务端如何装 batch

下面是从 `pre_decode()` 抽出来的简化逻辑（真实代码在 `server-context.cpp:3443` 附近）：

```cpp
// 简化版：把 slot 待处理的 prompt token 装进 batch
while (slot.prompt.n_tokens() < slot.task->n_tokens() && batch.size() < n_batch) {
    llama_token cur_tok = input_tokens[slot.prompt.n_tokens()];
    // 装入：slot id、token、位置、是否要 logits
    batch.add(slot.id,
              cur_tok,
              slot.prompt.tokens.pos_next(),  // 下一个空位的位置
              slot.need_embd());              // embedding 模式要每个位置都输出
    slot.prompt.tokens.push_back(cur_tok);
}
```

**为什么这么设计**：把 batch 的「填什么」交给 `server_slot` 自己决定。slot 是并行的基本单位（见 §8 术语表），多个 slot 的 token 拼在同一个 batch 里一次 decode，可以摊薄每次前向的固定开销。这就是「continuous batching」的本质。

## 5. 逐段笔记（按调用图标号）

### ① 参数解析 `common/arg.cpp:930`
- 所有 `--xxx` 参数统一解析进 `common_params params`。
- 关键子结构：`params.model`（模型路径）、`params.sampling`（采样配置）、`params.speculative`（投机解码配置）。
- **为什么集中在一个结构体**：CLI、server、example 都共用 `common_params`，避免每个入口各写一套解析。新增参数只要改一个文件。

### ② 后端初始化 `src/llama.cpp:89, 104`
- `llama_backend_init()`：初始化 ggml 时间表、加载已编译的后端（CPU/CUDA/Metal/Vulkan）。
- `llama_numa_init(strategy)`：让 CPU 后端绑定 NUMA 节点；多路 CPU 服务器上能避免跨 socket 内存访问。
- **为什么分开**：后端初始化只发生一次，NUMA 策略按用户参数选。解耦后 server 可以重复调用 `llama_numa_init` 切策略而不重置后端。

### ③ 模型加载 `server-context.cpp:998`
- `llama_model_load_from_file()`：解析 GGUF 头、张量元数据，张量按需懒分配（mmap，见 §6）。
- `llama_init_from_model()` (`src/llama-context.cpp:3490`)：构造 `llama_context`，内部主要做 3 件事：
  - **KV cache**：`memory.reset(model.create_memory(...))`（`src/llama-context.cpp:333`、`src/llama-model.cpp:2003`），按 `type_k/type_v` 与 `n_ctx × n_seq_max` 切分；显存占用大头。
  - **计算 buffer**：分两块——
    - `output_reserve()` (`src/llama-context.cpp:2062`) 分配 logits / embd / sampling 视图（每条 sequence × vocab 的 float 缓冲）。
    - `sched_reserve()` (`src/llama-context.cpp:439`) 触发 scheduler 用最坏 batch 跑一次空图，把每个后端的 scratch buffer 锁到峰值。
  - **后端采样器池**：`sampling` 结构（`src/llama-context.h:303` 的 `sampling_info`）。`samplers` 是 `std::map<llama_seq_id, llama_sampler*>`——按 seq 维护 sampler chain；`token_ids_full_vocab` 是全词表 id 表（用于 grammar 加速）；grammar 作为 `llama_sampler_grammar` 挂在 sampler chain 上，**不是 context 独立持有的成员**。
- 产物：`server_context::impl->ctx_tgt`（目标推理上下文）。

### ④ 一次 decode 的两阶段
每轮 `update_slots()` 里，**prompt 阶段**与**生成阶段**共用同一套 `pre_decode() -> decode() -> post_decode()` 三段式：
- **pre_decode()** (`server-context.cpp:2831`)：装 batch 前的预处理——context-shift、checkpoint 决策、tokenize。
- **decode()** (`server-context.cpp:3578`)：把 batch 喂给 `llama_decode` -> 构图 -> 后端执行前向，产出 logits。
- **post_decode()** (`server-context.cpp:3702`)：取 logits -> `common_sampler_sample` 选出下一个 token -> `accept` 更新采样器状态 -> `process_token` 判停 -> 流式回发。

## 6. mmap 懒加载与 `sched_reserve` 峰值预留

这两件事都发生在「模型加载完、用户提问前」的初始化阶段，初学者很容易忽略它们对性能的影响。

### 6.1 mmap 懒加载

`llama_model_loader` 构造函数（`src/llama-model-loader.cpp:512`）在 `use_mmap=true` 时（行 817）把整个 GGUF 文件 `mmap` 进虚拟地址空间，但**内核只在真正访问某页时才把它从磁盘读进物理内存**。

**为什么这么设计**：
- **快启动**：30 GB 的模型文件，`mmap` 调用本身瞬时返回，不必先把 30 GB 都读进内存。
- **按需加载**：只有 prompt 走过的层才会被换入。如果你只跑一个 64 token 的 prompt，未触达的层永远不会进物理内存。
- **多进程共享**：同一文件多个进程 mmap，内核只缓存一份页（除非用了 `MAP_PRIVATE` 写时复制，权重是只读的所以共享）。

代价是首次访问会有缺页中断（page fault）。生产环境里通常会先跑一次「warmup」decode 把权重全部触发一遍，对应 `llama_model_params.warmup`（`include/llama.h` 附近）和 `mparams.warmup` 在 `server-context.cpp:1041` 的传递。

### 6.2 `sched_reserve()`：跑空图测峰值

`sched_reserve()` (`src/llama-context.cpp:439`) 干的事有点反直觉：**在用户提问之前，先用最坏情况下的 batch 大小构造一张假图，让后端 scheduler 分配最大的 scratch buffer**。

具体步骤（行 452–635）：
1. 取 `n_tokens = min(n_ctx, n_ubatch)`、`n_seqs = n_seq_max` 作为最坏 batch 形状。
2. `graph_reserve(n_tokens, n_seqs, n_outputs, ...)`（行 612）构造一张空跑图。
3. `ggml_backend_sched_new(...)`（行 462）按这张图给每个后端分配 scratch。
4. 还会再跑一次「token generation」最坏图（行 632，`n_tokens=1`）记录节点数和 split 数。

**为什么这么设计**：ggml 的 scheduler 需要为每个算子的中间张量分配 buffer。如果运行时才探测，每次 `decode()` 都可能触发 buffer 重分配，导致性能抖动甚至 OOM。提前用峰值形状把 buffer 锁死，后续真实 decode 的图节点数一定**小于等于**预留值，scratch 不会再涨。

代价是显存占用偏保守——你看到的「compute buffer size = X MiB」日志就是这里测出来的，比实际需要的略大。

## 7. `pre_decode` / `decode` / `post_decode` 三段式

这三段是 `update_slots()` 主循环的核心。理解它们各自「解决什么问题」就理解了整个推理引擎。

### 7.1 `pre_decode()` 解决「这轮该跑哪些 token」

`server-context.cpp:2831` 的 `pre_decode()` 做四件事：

1. **context-shift**（行 2834–2899）：如果某 slot 的 prompt 已经撑满 `n_ctx`，按 `n_keep` 保留开头、丢弃中段、回填末尾，对应 `common_context_seq_rm` / `common_context_seq_add`（行 2873–2874）。这是「上下文窗口太小时滑窗」的实现。
2. **batch.clear()**（行 2902）：每轮重新组装。
3. **分类 slot**（行 2911–2968）：把 slot 分成 `generating`（已生成中）和 `drafting`（投机解码草稿）。投机解码的草稿 token 也在这轮被请求。
4. **装 batch**（行 3356–3572）：对每个 slot 调 `batch.add(...)` 把待处理 token 装进去，同时决定是否在装完后建 checkpoint。

> 为什么不直接把 batch 拼装放到 `decode()` 里？因为 `decode()` 只关心「这批 token 跑前向」，不想知道「为什么要跑这些 token」。把调度逻辑剥离出来，`decode()` 才能保持纯粹——同一份 `decode()` 既能跑 prompt 也能跑生成，既能跑单 slot 也能跑多 slot。

### 7.2 `decode()` 解决「把 batch 喂给前向」

`server-context.cpp:3578` 的 `decode()` 是个薄壳：

```cpp
bool decode(int32_t & n_batch, int32_t off, llama_batch & batch_view) {
    if (slot_batched) {
        common_set_adapter_lora(ctx_tgt, slot_batched->lora);  // LoRA 切换
        llama_set_embeddings(ctx_tgt, slot_batched->need_embd());
    }
    if (batch.size() == 0) return true;        // 空批直接跳过
    const int ret = llama_decode(ctx_tgt, batch_view);  // 行 3612
    if (ret != 0) {
        // ret == 1: KV 没空间，缩小 batch 重试
        // ret <  0: 真错误，抛异常
        ...
        n_batch /= 2;
        return false;  // 上层 update_slots 会用更小的 n_batch 重试
    }
    return true;
}
```

**返回值的语义**（对照 `include/llama.h:953-958` 的注释）：
- `0` 成功；
- `1` KV 没空槽——上层把 `n_batch` 减半重试（行 3658）；
- `2` aborted；
- `-1` 输入非法；
- `< -1` 致命错误。

`llama_decode()` 的 C API 在 `src/llama-context.cpp:4054`，转给 `llama_context::decode()`（行 1680）。后者才是真干活的地方——`balloc->init` 整理 token、`sched_reserve()` 检查是否需要重预留、`memory->init_batch` 给 KV cache 划槽、`build_graph` 构图、`graph_compute` 跑。

### 7.3 `post_decode()` 解决「从 logits 到下一个 token」

`server-context.cpp:3702` 的 `post_decode()` 遍历每个 slot，做四件事（行 3723–3810）：

1. **跳过不在本子 batch 的 slot**（行 3731）：因为 batch 可能被 `n_batch` 切成多段子批，每段 `post_decode` 只处理落在自己范围内的 slot。
2. **状态机推进**（行 3736–3762）：`SLOT_STATE_DONE_PROMPT` 转 `SLOT_STATE_GENERATING`，投机解码分支跳过普通采样。
3. **采样**（行 3774–3779）：
   ```cpp
   id = common_sampler_sample(slot.smpl.get(), slot.ctx_tgt, tok_idx);
   common_sampler_accept(slot.smpl.get(), id, true);
   ```
4. **判停 + 发回**（行 3805）：`process_token()` 检查停止词/EOS/预算，决定是否继续；若继续，`send_partial_response()` 推 token 给客户端。

> 为什么采样要拆成 `sample` + `accept` 两步？因为采样器链里有**有状态**的成员（重复惩罚需要看历史、grammar 需要推进状态机）。`sample()` 是「问一次」，`accept()` 是「告诉它选了这个，更新内部状态」。投机解码还会出现「sample 出来但拒绝」的情况，两步分离才能正确回滚。
