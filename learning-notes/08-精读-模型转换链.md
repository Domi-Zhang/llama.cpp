# 精读：模型转换链（HF -> GGUF）

> 日期：2026-08-13
> 2026-08-17 修订：扩充为初学者详细版（张量映射例子等）
> 核心文件：`convert_hf_to_gguf.py`（入口）+ `conversion/base.py`（基类）+ `conversion/<arch>.py`（各架构）+ `gguf-py/`（GGUF 写库）
> 前置：已读 `07`，GGUF 是 llama.cpp 的模型格式，转换是「PyTorch/HF 权重 -> GGUF」的桥。

## 作用

把 Hugging Face 格式（safetensors + config.json + tokenizer）的模型权重、超参、词表，转成 llama.cpp 能直接加载的 `.gguf` 单文件。每个新架构要能在 llama.cpp 跑，都得先有对应的转换器。

## 0. 预备：HF 模型长什么样

在写转换器之前，先弄清「输入」是什么。一个典型的 HF 模型仓库（比如 `meta-llama/Llama-3.2-1B`）下载到本地是一个目录，里面大致有这些文件：

| 文件 | 作用 | 转换器关心什么 |
|---|---|---|
| `config.json` | 模型超参（层数、维度、头数、激活、RoPE 配置等）+ `model_type`/`architectures` 字段标识架构 | `ModelBase.load_hparams` 读它得到 `self.hparams`，再据此选架构子类 |
| `*.safetensors` | 权重本体，可能分片成 `model-00001-of-00003.safetensors` 等；附 `model.safetensors.index.json` 描述每个张量在哪一片 | `index_tensors` 逐片扫描，按张量名建立「惰性加载器」字典 |
| `tokenizer.json` | BPE/HuggingFace fast tokenizer 的合并表与词表 | `_set_vocab_gpt2` 走这条分支 |
| `tokenizer.model` | SentencePiece 模型（LLaMA 1/2、Gemma 等用） | `_set_vocab_sentencepiece` 走这条分支 |
| `tokenizer_config.json` | special token、chat template、`add_prefix_space` 等运行期行为 | 写入 KV；也用于检测特殊 tokenizer 类（如 `HybridDNATokenizer`） |
| `special_tokens_map.json` | bos/eos/pad/unk 的 token id 映射 | `gguf.SpecialVocab` 自动加载并写入 KV |
| `generation_config.json` | 默认采样参数 | 转换器一般不读，运行时由 server 处理 |
| `pytorch_model.bin`（老格式） | 早期 `.bin` 用 `torch.save`（pickle）存权重 | `index_tensors` 在没有 safetensors 时回退到这条路径 |

`safetensors` 之外的所有文件都是 JSON 或文本，工具链很容易读。权重文件才是大头，所以下面专门讲。

### 为什么 GGUF 要打包成单文件

HF 的「一个目录里十几个文件」对训练友好（分片下载、增量更新、tokenizer 与权重解耦），但对推理不友好：

1. **分发**：用户要拷贝/下载一整个目录，容易漏文件、版本错配（tokenizer 与权重对不上）。
2. **加载**：llama.cpp 是 C++ 写的，不想依赖 HuggingFace `transformers` 那套 Python 解析逻辑。把所有东西塞进一个二进制文件，C++ 端只要 `mmap` 一次就能拿到全部张量。
3. **mmap 友好**：GGUF 把张量数据连续排列、对齐到 32 字节（`GGUF_DEFAULT_ALIGNMENT = 32`，`gguf-py/gguf/constants.py:12`），操作系统可以按页惰性加载，大模型只在实际用到某层时才把那页读进内存。目录式存储做不到这种「整文件 mmap + 按需分页」。

所以 GGUF = 一个二进制容器，把「超参 + 词表 + 张量」三件套按固定格式塞进去，让 C++ 加载器无需任何外部依赖就能跑模型。转换器就是「目录 -> 单文件」的桥。

### 一个张量的旅程：从 `q_proj.weight` 到 `blk.0.attn_q.weight`

光看流程图还是抽象。下面以 Llama 的第 0 层 query 投影矩阵为例，跟一个具体张量走一遍。HF 里它叫 `model.layers.0.self_attn.q_proj.weight`，转换到 GGUF 后变成 `blk.0.attn_q.weight`。这两条名字是怎么对上的？

**第 1 步：HF 端的索引建立（`conversion/base.py:198 index_tensors`）**

`index_tensors` 遍历所有 safetensors 分片，把每个张量的「名字 + 惰性加载器」塞进 `self.model_tensors` 字典。此时张量数据还没真读进内存，只记了一个能按需 mmap 的闭包。

**第 2 步：bid 提取（`conversion/base.py:874-879`）**

`prepare_tensors` 在主循环里把名字按 `.` 切开，取第一个十进制片段作为 `bid`（block id）：

```python
bid = None
for part in name.split("."):
    if part.isdecimal():
        bid = int(part)
        break
```

对 `model.layers.0.self_attn.q_proj.weight`，`bid = 0`。

**第 3 步：架构相关的预处理（`conversion/llama.py:218 modify_tensors`）**

LlamaModel 的 `modify_tensors` 重写了基类钩子。对 Q/K 投影权重，它会做一次 `permute`（见下文「常见坑」一节），然后调基类的 `modify_tensors`。这一步处理的是「同样的张量在不同架构里物理布局可能不同」，是架构子类的责任。

**第 4 步：名字映射（`conversion/base.py:606 map_tensor_name` -> `tensor_mapping.py:2458 get_name`）**

基类 `modify_tensors`（`base.py:615`）调用 `map_tensor_name(name)`，传入完整的 HF 名字 `model.layers.0.self_attn.q_proj.weight`：

```python
def map_tensor_name(self, name, try_suffixes=(".weight", ".bias")):
    new_name = self.tensor_map.get_name(key=name, try_suffixes=try_suffixes)
    if new_name is None:
        raise ValueError(f"Can not map tensor {name!r}")
    return new_name
```

`self.tensor_map` 是 `gguf.get_tensor_name_map(self.model_arch, self.block_count)` 在 `TextModel.__init__`（`base.py:1116`）里建的 `TensorNameMap` 实例。它的构造函数（`tensor_mapping.py:2425`）做了两件事：

1. 把 GGUF 标准名（来自 `TENSOR_NAMES`，`constants.py:1099`）作为键值对的反向也注册进去，例如 `TENSOR_NAMES[MODEL_TENSOR.ATTN_Q] = "blk.{bid}.attn_q"`，对 `bid=0` 就得到 `"blk.0.attn_q"`，登记为 `mapping["blk.0.attn_q"] = (ATTN_Q, "blk.0.attn_q")`。
2. 把所有可能的 HF 别名（来自 `block_mappings_cfg`，`tensor_mapping.py:255-272` 那一段）也登记成同样的目标，例如 `mapping["model.layers.0.self_attn.q_proj"] = (ATTN_Q, "blk.0.attn_q")`。

`get_name` 在查表时会先试完整 key 失败，再剥掉 `.weight` 后缀重试。所以：

- 输入 `model.layers.0.self_attn.q_proj.weight`
- 剥后缀 -> `model.layers.0.self_attn.q_proj`
- 查表命中 -> 返回 `"blk.0.attn_q" + ".weight"` = `"blk.0.attn_q.weight"`

**第 5 步：量化与写入（`base.py:964-979`）**

拿到新名字后，`prepare_tensors` 根据 `self.ftype`（如 `MOSTLY_Q8_0`）选 `data_qtype`，调用 `gguf.quants.quantize(data, data_qtype)` 把 float 数组转成量化字节流，最后 `self.gguf_writer.add_tensor(new_name, data, raw_dtype=data_qtype)` 登记进 GGUF writer。

### 为什么命名要统一

GGUF 张量名是个跨语言契约：Python 转换器写什么名，C++ 加载器就得按同样的名查表。具体对应关系在两处定义，必须保持一致：

- **写端**：`gguf-py/gguf/constants.py:1099` 的 `TENSOR_NAMES` 字典，例如 `MODEL_TENSOR.ATTN_Q: "blk.{bid}.attn_q"`（`constants.py:1116`）。
- **读端**：`src/llama-arch.cpp:359` 的 `LLM_TENSOR_NAMES`，例如 `{ LLM_TENSOR_ATTN_Q, "blk.%d.attn_q" }`（`llama-arch.cpp:366`），由 `LLM_TN` 辅助结构（`src/llama-arch.h:607`）格式化成完整名。

加载时 `llama_model::load_arch_tensors`（`src/llama-model.cpp:1315`）按这些名字从 GGUF 里取张量，名字对不上就直接报「tensor not found」。这就是为什么新增模型要同时改 Python 端（`constants.py` + `tensor_mapping.py` + `conversion/<arch>.py`）和 C++ 端（`llama-arch.h/cpp` + `llama-model.cpp`）——契约两端必须同步。

## 一、架构映射与抽象（`conversion/base.py`）

`ModelBase`（`base.py:75`）是抽象基类，定义子类必须实现的钩子：

| 方法 | 行号 | 作用 |
|---|---|---|
| `set_vocab` | `base.py:1162`（TextModel 默认走 GPT2） | 写词表（BPE/SentencePiece）到 KV |
| `set_gguf_parameters` | `base.py:612`（抽象）/ `:1193`（TextModel 默认） | 写超参（维度/层数/头数...）到 KV |
| `set_tensors` | （由 `prepare_tensors` + `modify_tensors` 协作） | 把 HF 张量按 GGUF 命名规则写入 |
| `modify_tensors` | `base.py:615`（默认实现仅改名） | 预处理某个张量（转置/重命名/拆分） |
| `format_tensor_name` | `base.py:584` | HF 名 -> gguf.MODEL_TENSOR 名映射（按枚举查 `TENSOR_NAMES`） |
| `map_tensor_name` | `base.py:606` | 通过 `tensor_map` 把 HF 完整名映射成 GGUF 完整名 |
| `filter_tensors` | `base.py:569` / `:1146` | 在 indexing 阶段过滤/改名（如剔除视觉塔张量） |

每个架构一个子类（`conversion/llama.py`、`qwen.py`、`gemma.py`...），用 `@ModelBase.register(...)` 装饰器（`base.py:1075`）注册到名字表。装饰器的参数是 HF `config.json` 里 `architectures` 字段可能出现的值，比如 Llama 模型会被标成 `"LlamaForCausalLM"`，所以注册成：

```python
@ModelBase.register(
    "LLaMAForCausalLM", "LlamaForCausalLM", "MistralForCausalLM",
    "MixtralForCausalLM", "VLlama3ForCausalLM", ...
)
class LlamaModel(TextModel):
    model_arch = gguf.MODEL_ARCH.LLAMA
```

`get_model_class`（`base.py:1093 from_model_architecture`）按 config 里的 `architectures[0]` 查 `_model_classes[ModelType.TEXT]` 字典找到对应子类。`main()`（`convert_hf_to_gguf.py:242`）就调它来取类、实例化、调 `write()`。

### 新增一个架构的最小步骤清单

要把一个新模型（假设叫 `FooForCausalLM`）接入 llama.cpp，转换器侧至少要做这些事（与官方教程 `docs/development/HOWTO-add-model.md` 对应）：

1. **在 `gguf-py/gguf/constants.py` 注册架构枚举**：
   - `MODEL_ARCH`（`:395`）加一项 `FOO`。
   - `MODEL_ARCH_NAMES`（`:952`）加人 friendly 名 `"foo"`。
   - `MODEL_TENSORS`（搜索同文件）列出该架构用到的 `MODEL_TENSOR.*`，这决定了哪些标准名会被 `tensor_map` 注册。

2. **在 `gguf-py/gguf/tensor_mapping.py` 加 HF 别名**：如果新模型的 q_proj 起了不同的名字（比如 `encoder.layers.{bid}.attn.query`），在对应的 `MODEL_TENSOR.ATTN_Q` 元组里追加这条别名。

3. **在 `conversion/foo.py` 写子类**：
   ```python
   @ModelBase.register("FooForCausalLM")
   class FooModel(TextModel):
       model_arch = gguf.MODEL_ARCH.FOO

       def set_gguf_parameters(self):
           super().set_gguf_parameters()
           # 加 Foo 特有的超参，如：
           self.gguf_writer.add_some_foo_param(self.hparams["foo_param"])

       def set_vocab(self):
           # 选 BPE 或 SPM 分支
           self._set_vocab_sentencepiece()  # 或 _set_vocab_gpt2()

       def modify_tensors(self, data_torch, name, bid):
           # 处理 Foo 特殊的张量布局，最后调 super().modify_tensors 走标准映射
           yield from super().modify_tensors(data_torch, name, bid)
   ```

4. **C++ 加载端**：在 `src/llama-arch.h` 加 `LLM_ARCH_FOO` 枚举，在 `src/llama-arch.cpp` 加 `LLM_ARCH_NAMES` / `LLM_TENSOR_NAMES` 条目，在 `src/llama-model.cpp` 写 `build_arch_graph` 并在 `llama_model_mapping` 注册。这一步与转换器对称——详见 `HOWTO-add-model.md` 的第 2、3 节。

> 设计：**新增架构 = 写一个新 Python 子类 + C++ 端对称注册**。子类实现 `set_vocab` / `set_gguf_parameters` / `modify_tensors` 三个钩子，其余复用基类；如果架构用了 `MODEL_TENSOR` 里没有的新张量类型，还要在 `constants.py` 和 `tensor_mapping.py` 里加新枚举和映射。

## 二、safetensors 读取：格式与惰性加载

权重是转换器最大的输入，单独说一下它怎么读。

### safetensors 文件格式

safetensors 的设计目标就是「无 pickle 安全加载」。文件结构非常简单（参考 `gguf-py/gguf/utility.py:290 SafetensorsLocal` 的解析逻辑）：

```
+----------------------+
| 8 字节小端无符号整数  |  = 后面 JSON header 的字节长度 N
+----------------------+
| N 字节 JSON header    |  形如 {"tensor_name": {"dtype": "F16", "shape": [4096,4096], "data_offsets": [0, K]}, ...}
+----------------------+
| 张量数据区（连续）     |  按 data_offsets 切片定位每个张量
+----------------------+
```

`SafetensorsLocal.__init__`（`utility.py:300`）做的事：

1. 读前 8 字节得 `metadata_length`。
2. 读 `metadata_length` 字节 JSON，解析成 `dict[str, dict]`。
3. 对每个张量条目，记录 `(dtype, shape, LocalTensorRange(filename, offset, size))` 到 `self.tensors`。

注意它**没有**像 `torch.load` 那样反序列化 Python 对象，只解析了一段 JSON 描述。这是 safetensors 相对老式 `.bin`（`torch.save` 用 pickle）的主要安全动机：pickle 可以执行任意代码，safetensors 只是数据。

### mmap 惰性读取

`LocalTensor.mmap_bytes`（`utility.py:286`）返回一个 `np.memmap`，把文件的一段映射成 numpy 数组视图：

```python
def mmap_bytes(self) -> np.ndarray:
    return np.memmap(self.data_range.filename, mode='c',
                     offset=self.data_range.offset, shape=self.data_range.size)
```

`mode='c'` 是 copy-on-write，读时不真正载入内存，只有访问到那页时操作系统才按需读盘。`index_tensors` 把每个张量包成 `LazyTorchTensor.from_local_tensor(data)`（`base.py:2560`）的闭包存进 `self.model_tensors`，到 `prepare_tensors` 真正调 `gen()` 时才物化成 torch tensor。

对几十 GB 的大模型，这套机制意味着转换器只需要几十 MB 的 Python 内存峰值——每个张量读完、量化完、写出去就丢掉，再换下一个。`--no-lazy` 会强制一次性物化所有张量，正常情况不要开。

`--remote` 模式（`convert_hf_to_gguf.py:184`）走的是 `gguf.utility.SafetensorRemote`（`utility.py:93`），原理类似，但通过 HuggingFace Hub API 按字节范围远程拉取，连下载都省了。

## 三、GGUF 文件三段结构（`write()` :1022）

GGUF 是二进制容器，`ModelBase.write`（`base.py:1022`）按三段写入：

1. **Header**（`gguf_writer.py:214 write_header_to_file`）：魔数 `GGUF`（`0x46554747`，`constants.py:10`）、版本（`GGUF_VERSION = 3`，`:11`）、tensor 数量、KV 数量。每个值都是定长小端二进制。
2. **KV metadata**（`gguf_writer.py:237 write_kv_data_to_file`）：统一键值对（架构名、超参、tokenizer 配置、量化类型）。值类型由 `GGUFValueType` 枚举标识（UINT32/STRING/ARRAY...），读写两端按类型编解码。
3. **Tensor info + Tensor data**（`gguf_writer.py:254 write_ti_data_to_file` + `:438 write_tensors_to_file`）：每个张量先写「名称、形状、dtype、偏移」描述，再按对齐填充写实际数据。

张量名遵循 `gguf.MODEL_TENSOR` 枚举（`constants.py:544`），通过 `TENSOR_NAMES`（`:1099`）映射成字符串，如 `token_embd.weight`、`blk.0.attn_q.weight`、`blk.0.ffn_gate.weight`。这些名与 `src/llama-arch.cpp:359` 的 `LLM_TENSOR_NAMES` 里 `LLM_TENSOR_*` 一一对应——这也是转换器与加载器能对上的关键约定（见上文「为什么命名要统一」）。

## 四、量化发生在转换时

很多用户会直接用 `python convert_hf_to_gguf.py model/ -o q8_0` 一步到位产出量化模型，不用再跑 `llama-quantize`。这条路径走的是 `prepare_tensors` 里的小段分发逻辑（`base.py:948-969`）：

```python
if isinstance(data_qtype, bool):
    if self.ftype == gguf.LlamaFileType.ALL_F32:
        data_qtype = gguf.GGMLQuantizationType.F32
    elif self.ftype == gguf.LlamaFileType.MOSTLY_F16:
        data_qtype = gguf.GGMLQuantizationType.F16
    elif self.ftype == gguf.LlamaFileType.MOSTLY_BF16:
        data_qtype = gguf.GGMLQuantizationType.BF16
    elif self.ftype == gguf.LlamaFileType.MOSTLY_Q8_0:
        data_qtype = gguf.GGMLQuantizationType.Q8_0
    ...
data = gguf.quants.quantize(data, data_qtype)  # :965
```

`ftype` 在 `convert_hf_to_gguf.py:204` 的 `ftype_map` 里从命令行 `--outtype` 字符串映射成 `gguf.LlamaFileType` 枚举。`auto` 模式（`GUESSED`）会先扫一遍张量 dtype，按是 bf16 还是 f16 自动选（`base.py:160-175`）。

`gguf.quants.quantize`（`quants.py:57`）按 `data_qtype` 查 `_type_traits` 字典找到对应的 `__Quant` 子类，调它的 `quantize` 类方法。以 Q8_0 为例（`quants.py:379`）：

```python
class Q8_0(__Quant, qtype=GGMLQuantizationType.Q8_0):
    @classmethod
    def quantize_blocks(cls, blocks: np.ndarray) -> np.ndarray:
        d = abs(blocks).max(axis=1, keepdims=True) / 127
        id = np.where(d == 0, 0, 1 / d)
        qs = np_roundf(blocks * id)
        d = d.astype(np.float16).view(np.uint8)
        qs = qs.astype(np.int8).view(np.uint8)
        return np.concatenate([d, qs], axis=1)
```

每 32 个浮点数一个块：算出 `d = max/127`（fp16，2 字节），把每个数除以 `d` 四舍五入成 int8（32 字节），共 34 字节——这正是 `06-精读-量化系统` 里讲的 Q8_0 block 格式。`block_size=32, type_size=34` 来自 `GGML_QUANT_SIZES` 表（`constants.py`），`__Quant.__init_subclass__`（`quants.py:92`）自动读出来挂在类上。

所以转换时量化 = 在 Python 端按完全相同的 block 布局编码，写出来的 GGUF 直接就是 C++ 后端能识别的量化张量，运行时无需再量化。`-o f16`/`bf16`/`f32` 同理，只是把数据转成对应浮点格式不含量化。

特殊规则（`base.py:889-946`）会强制某些张量保持 F32：1D 张量、norm 权重、`FFN_GATE_INP`、`SSM_CONV1D`、`POSITION_EMBD` 等对精度敏感的层。这些规则「与 `llama_model_quantize_internal` 保持一致」——也就是说，转换时量化和后量化走的是同一套豁免清单，结果应当一致。

## 五、词表导出（`set_vocab` 分支）

词表写入由子类的 `set_vocab` 负责（抽象方法在 `base.py:1019`，TextModel 默认在 `:1162` 调 `_set_vocab_gpt2`）。基类提供了一组 `_set_vocab_*` 辅助函数，覆盖主流 tokenizer 类型：

- **GPT2/BPE**（`base.py:1706 _set_vocab_gpt2`）：从 `tokenizer.json` 读词表与 merges，写入 `tokenizer_model = "gpt2"` + token list + merges。Llama 3、Qwen、Mistral 大多走这条。
- **SentencePiece**（`base.py:1823 _set_vocab_sentencepiece`）：从 `tokenizer.model`（protobuf）读，写入 `tokenizer_model = "llama"` + token list + scores + toktypes。Llama 1/2、Gemma 走这条。
- **Llama-HF 混合**（`base.py:1925 _set_vocab_llama_hf`）：先尝试 SPM，再退到 GPT2。
- **Mistral 官方**（`base.py:2152 _set_vocab_mistral`）：用 `mistral-common` 库读 tekken.json 或 consolidated.spm.model。
- 其他：`_set_vocab_qwen`、`_set_vocab_rwkv_world`、`_set_vocab_hybriddna`、`_set_vocab_builtin` 等专门分支。

Llama 的 `set_vocab`（`conversion/llama.py:92`）展示了典型的选择逻辑：先按 `origin_hf_arch` 和是否 mistral 分流，再尝试 SPM -> Llama-HF -> GPT2 的回退链。

词表的内部数据结构、special token 处理、`gguf.SpecialVocab` 的合并逻辑等细节在 `11-精读-词表与Tokenizer` 里详讲，这里只指出「分支由 tokenizer 文件类型决定」。

## 六、常见坑

### dtype 选择：f32 / f16 / bf16 / q8_0

`--outtype` 决定输出 dtype。几条经验：

- **`auto`（默认）**：转换器扫第一个 2D 张量的 dtype 来决定 f16 还是 bf16（`base.py:160-175`）。注意它**不读 `config.json` 里的 `torch_dtype`**——很多微调模型这个字段会撒谎。
- **`bf16` vs `f16`**：现代模型（Llama 3、Qwen 2+）训练时基本都用 bf16，转 f16 会丢精度（特别是 norm 层的极小值）。优先选 bf16。
- **`q8_0`**：体积约为 f16 的一半，推理速度通常更快，质量损失很小。如果只是想跑推理、不打算再量化，直接 `q8_0` 一步到位最省事。
- **`f32`**：只在调试或与原模型逐位对比时用，体积是 f16 的两倍。

### 张量转置：为什么 Llama 要 `permute` Q/K

`conversion/llama.py:32 undo_permute = True`，`modify_tensors`（`:243-247`）会对 `q_proj.weight` 和 `k_proj.weight` 做一次 `permute`：

```python
if self.undo_permute:
    if name.endswith(("q_proj.weight", "q_proj.bias")):
        data_torch = LlamaModel.permute(data_torch, n_head, n_head)
    if name.endswith(("k_proj.weight", "k_proj.bias")):
        data_torch = LlamaModel.permute(data_torch, n_head, n_kv_head)
```

原因：HF/PyTorch 里 Q/K 权重按 `(n_head, head_dim, n_embd)` 排布，而 llama.cpp 的 RoPE 实现假设权重已经按「每对 head 交错」排布。`permute`（`:162`）就是把这个交错解开。`tensor_mapping.py:258` 那条 `model.layers.{bid}.self_attn.q_proj_no_perm` 别名就是给已经预排布好的自定义 checkpoint 用的，对应 `Llama4Model.undo_permute = False`（`llama.py:361`）。

类似地，`Llama4Model.modify_tensors`（`llama.py:381`）会拆 `gate_up_proj` 成 `gate_proj` + `up_proj`，并对 `down_proj` 做 `transpose(-1, -2)`——因为 Llama 4 在 HF 端存的是 `(out, in)` 而 llama.cpp 期望 `(in, out)`。遇到「转换出来的模型 perplexity 异常」时，先检查这类布局差异。

### `--dry-run` 调试

加 `--dry-run`（`convert_hf_to_gguf.py:96`）会让 GGUFWriter 不真正写盘，只打印分片计划与张量列表。这对调试很有用：

- 想确认架构子类有没有被选对、张量名映射有没有命中、哪些张量被强制 F32、哪些走量化——`--dry-run --verbose` 会在日志里全部列出。
- 想验证一个新架构子类而不浪费磁盘空间，先 `--dry-run` 跑通再正式转。
- 配合 `--vocab-only` 可以单独测词表分支是否正确。

如果 `modify_tensors` 漏掉了某个张量没 yield 出来，`prepare_tensors` 不会报错（它只迭代 `get_tensors` 的产出），但 GGUF 里就缺这个张量，加载时 C++ 端会报 `tensor not found`。`--dry-run` 的张量列表能帮你提前发现这种遗漏。

## 关键点速查

- **量化发生在转换时**：`-o q8_0` 等会调用 gguf-py 内部的量化（对应 `06` 的 block 格式），转出的就是已量化权重。
- **懒加载/远程**：`--remote` 直接从 HF 拉文件；`--lazy`（默认开）用 safetensors mmap 逐张量读，避免一次载入全部内存。
- **分片**：`--split-max-size` 可把大模型拆成多文件 GGUF。
- **词表**：`--vocab-only` 只导出词表；词表格式（BPE/SPM）决定 `set_vocab` 的分支。
- **与加载器对称**：转换器写什么名/类型，`load_arch_tensors` 就按同样名/类型读，两端必须一致。

## 图视角小结（全链路闭环）

```
conversion (<arch>.py)  ─写─>  GGUF 文件  ─读─>  src/models/<arch>.cpp load_arch_tensors
   HF 张量名/超参              三段结构           llama.cpp 张量名 LLM_TENSOR_*
   (model.layers.0...          (Header+KV+        (blk.0.attn_q.weight)
    self_attn.q_proj.weight)   Tensor data)
        ↑                          ↑                      ↑
   tensor_mapping.py           gguf_writer.py        llama-arch.cpp:359
   block_mappings_cfg          write_*_to_file       LLM_TENSOR_NAMES
```

- 转换链是「模型入库」的入口，`docs/development/HOWTO-add-model.md` 是官方教程。
- 理解它，就能理解「为什么新增一个模型要改转换器 + 加载器 + 构图」三处。
- 关键契约：`gguf-py/gguf/constants.py:1099 TENSOR_NAMES` 与 `src/llama-arch.cpp:359 LLM_TENSOR_NAMES` 是同一份名字表的两端镜像，任何一端改动都要同步另一端。
