## 0. 为什么「能」量化，省在哪里

要先建立两个直觉，否则后面所有公式都是空中楼阁。

### 0.1 权重是访存大头，不是算力大头

LLM 推理在 batch=1（典型对话场景）下，瓶颈不是乘加算力，而是**把权重从显存搬到 SM/CPU 核心的时间**。原因：

- 每生成 1 个 token，模型的所有权重都要被「读一遍」。FFN 层的 `W_up`、`W_down`、attention 的 `W_q/K/V/O`、embedding 全部参与一次 matmul。
- 而 KV-cache、激活值只占很小一部分（batch=1 时激活值是「每层 1 行」，远小于权重矩阵）。
- 所以单 token 的下限耗时 ≈ `权重总字节 / 内存带宽`。

**带宽 = 字节数 x 频率**。频率由硬件固定，能动手脚的只有「字节数」。把每个权重从 16 bit 压到 4 bit，字节数直接砍 1/4，理论生成速度也快 4 倍（在访存受限时）。

### 0.2 数字例子：7B 模型 f16 vs Q4_0

Llama-2-7B 大约 6.7 B 权重：

| 格式 | 每权重 bit | 每权重字节 | 总体积 | 每 token 读取量 |
|---|---|---|---|---|
| FP16 | 16 | 2 | ~13.4 GB | ~13.4 GB |
| Q4_0 | 4.5（推导见 §2） | 0.5625 | ~3.77 GB | ~3.77 GB |

在 1 TB/s 带宽的 GPU（A100 量级）上，batch=1 单 token 理论下限：
- FP16：13.4 ms/token
- Q4_0：3.77 ms/token

在 ~50 GB/s 的 DDR4 内存（CPU 推理）上：
- FP16：~270 ms/token（约 4 token/s）
- Q4_0：~75 ms/token（约 13 token/s）

这就是「能量化」的根本原因——权重是访存大头，压缩权重就是直接提速。代价是精度损失（困惑度小幅上升），后面所有格式设计都是在「体积 vs 精度」之间做精细权衡。

## 1. 分层：编排 vs 内核

```
src/llama-quant.cpp        决定「哪个 tensor 用哪种类型」+ 多线程调度
  └─ ggml_quantize_chunk()   ggml 层：把一块 f32 数据按某类型量化

```

「编排」(llama-quant.cpp) 只关心：哪个张量该用什么类型、要不要回退、怎么切分给多线程。「内核」(ggml-quants.c) 只关心：给我 32 个 float，我吐出一个 block。两层解耦，新增格式只需在 ggml 层加一对 `quantize_row_*_ref` / `dequantize_row_*`。

## 2. block 格式（`ggml/src/ggml-common.h`）

### 2.1 为什么按 block 分组共享 scale

逐权重存 scale 没意义（scale 本身就占 16 bit，等于没压缩）。逐 tensor 存一个 scale 又太粗（一个 4096x4096 矩阵里权重幅度可能差几百倍，一个 scale 装不下）。折中：**每 N 个权重共享一个 scale**。

N 的选择是关键 trade-off：
- N 越小（如 32）：scale 越贴合局部权重幅度，误差小，但元数据（scale）占比高。
- N 越大（如 256）：元数据占比低，但一个 scale 管太多权重，幅度差异被「削峰填谷」，误差大。

llama.cpp 的做法：
- 朴素格式（Q4_0/Q5_0/Q8_0）用 **32** 一组。
- K 系列用 **256**（super-block），但内部再分 8 个 32-子块，子块各自有 scale——相当于「32 一组」的精度 + 「256 一组」的元数据效率（详见 §5）。

### 2.2 Q4_0 block 结构（ggml-common.h:184-188）

```c
#define QK4_0 32                 // 一个 block 装 32 个权重  (ggml-common.h:184)
typedef struct {
    ggml_half d;                 // delta：block 的共享缩放因子 (f16, 2 字节)
    uint8_t qs[QK4_0 / 2];       // 16 字节装 32 个 4-bit 量化值（每字节打包 2 个）
} block_q4_0;                    // 共 18 字节
```

### 2.3 bpw（bits per weight）推导

bpw = block 总位数 / block 内权重数。

Q4_0：
```
block 字节数 = sizeof(ggml_half) + QK4_0/2
            = 2 + 16
            = 18 字节
            = 144 bit
bpw = 144 / 32 = 4.5
```

那个 0.5 bit 就是 scale 的开销：每 32 个权重花 16 bit 存 scale，摊到每个权重就是 0.5 bit。

类似地可推：
- Q5_0：`2(d) + 4(qh) + 16(qs) = 22 字节 = 176 bit`，bpw = 176/32 = 5.5
- Q8_0：`2(d) + 32(qs) = 34 字节 = 272 bit`，bpw = 272/32 = 8.5（接近原始 int8）
- Q4_1：`2(d) + 2(m) + 16(qs) = 20 字节`，bpw = 160/32 = 5.0（多了 min 偏差）

| 类型 | 位数 | 是否有 min 偏差 | 说明 |
|---|---|---|---|
| `Q4_0` | 4.5 bpw | 无 | 对称，最简；`d` + 4bit 值 |
| `Q4_1` | 5.0 bpw | 有 `m` | 非对称，含 min 偏差 |
| `Q5_0`/`Q5_1` | 5.5/6.0 bpw | - | 5-bit，多一组 `qh` 存第 5 位 |
| `Q8_0` | 8.5 bpw | 无 | 高精度，常用作量化时的中间类型 |
| `Q2_K`/`Q3_K`/`Q4_K`/`Q5_K`/`Q6_K` | 2.6~7 bpw | 超块 | **K 系列**：多个子 block 共享超块 scale，精度/体积折中更好 |
| `NVFP4`/`MXFP4` | 4 bpw | - | 新硬件格式（英伟达/AMD） |

## 3. Q4_0 量化算法（`ggml-quants.c:75` quantize_row_q4_0_ref）

### 3.1 算法步骤

对每个 block 的 32 个权重（ggml-quants.c:75-110）：

```c
1. 找绝对最大值 amax 及其带符号原值 max     // :83-92
2. d  = max / -8                            // :94  缩放因子
3. id = 1/d                                 // :95
4. 每个权重 xi -> MIN(15, (int8_t)(xi*id + 8.5f))   // :103-104
5. 两个 4-bit 值打包进一个 uint8_t（低位 + 高位<<4）  // :106-107
```

反量化（dequantize_row_q4_0, :401-419）：
```c
x = ((qs & 0x0F) - 8) * d                   // :412, 415
```

### 3.2 公式细节解释（容易踩坑）

**为什么是 `max / -8`，不是 `max / 7` 或 `max / 8`？**

注意 `max` 是**带符号**的（保存了原始符号）。4-bit 无符号范围是 `[0, 15]`，反量化时减 8 变成 `[-8, 7]`——这是一个**不对称**区间：负方向能到 -8，正方向只能到 +7。

为了让「最大幅度的那个权重」精确落在一个端点上，作者选择让它落在 **-8 端**（更负的一侧）：
- 若 `max` 为正（如 +1.5）：`d = 1.5 / -8 = -0.1875`（d 为负）。反量化时 `(0-8)*d = -8 * -0.1875 = 1.5`，即 max 落在 qs=0。
- 若 `max` 为负（如 -1.2）：`d = -1.2 / -8 = 0.15`（d 为正）。反量化时 `(0-8)*d = -8 * 0.15 = -1.2`，max 也落在 qs=0。

所以无论 max 正负，`max` 总是映射到 qs=0，对侧（-max）则尝试映射到 qs=15，但 qs=15 反量化是 `7*d`，幅度只有 `7/8 * |max|`，会有损失。这是 Q4_0 的内置不对称：最大幅度的符号方向被精确表示，反方向有 1/8 的削峰。这是 Q4_0 简单但不够好的原因之一，K 系列用对称式 + min 偏差改善了这点。

**为什么 `+8.5f`？**

拆开看：`+8` 是把 `[-8, 7]` 平移到 `[0, 15]`（4-bit 无符号可表示范围）。`+0.5` 是四舍五入技巧——`(int8_t)` 是向零截断，加 0.5 后截断等价于 round 到最近整数。例如 `3.6 + 0.5 = 4.1`，截断得 4；`3.4 + 0.5 = 3.9`，截断得 3。

**为什么 `MIN(15, ...)`？**

极端情况下（如所有权重都接近 0，只有一个是 max），对侧 -max 算出的 `xi*id + 8.5` 可能等于 16.5，超出 4-bit 范围。MIN 钳到 15 防止溢出——这正是上面说的「对侧削峰」。

### 3.3 完整数值例子

取 4 个权重 `x = [0.5, -1.2, 0.3, -0.8]`（为简化只演示 4 个，实际 block 是 32 个，算法完全相同）。

**步骤 1：求 amax / max**

| xi | |xi| | 当前 amax | 当前 max |
|---|---|---|---|
| 0.5 | 0.5 | 0.5 | 0.5 |
| -1.2 | 1.2 | 1.2 | -1.2 |
| 0.3 | 0.3 | 1.2 | -1.2 |
| -0.8 | 0.8 | 1.2 | -1.2 |

最终：`amax = 1.2`，`max = -1.2`（带符号）。

**步骤 2：算 d 和 id**

```
d  = max / -8 = -1.2 / -8 = 0.15
id = 1 / d    = 6.6667
```

**步骤 3：量化每个权重**

公式 `qs = MIN(15, (int8_t)(xi * id + 8.5))`：

| xi | xi*id | +8.5 | (int8_t) | MIN(15,·) | 最终 qs |
|---|---|---|---|---|---|
| 0.5 | 3.333 | 11.833 | 11 | 11 | 11 |
| -1.2 | -8.000 | 0.500 | 0 | 0 | 0 |
| 0.3 | 2.000 | 10.500 | 10 | 10 | 10 |
| -0.8 | -5.333 | 3.167 | 3 | 3 | 3 |

量化值：`[11, 0, 10, 3]`。

**步骤 4：反量化**

公式 `x_hat = (qs - 8) * d`：

| qs | qs-8 | *d (0.15) | x_hat | 原 x | 误差 |
|---|---|---|---|---|---|
| 11 | 3 | 0.45 | 0.45 | 0.5 | 0.05 |
| 0 | -8 | -1.20 | -1.20 | -1.2 | 0.00 |
| 10 | 2 | 0.30 | 0.30 | 0.3 | 0.00 |
| 3 | -5 | -0.75 | -0.75 | -0.8 | 0.05 |

最大误差 0.05，相对幅度约 4%。注意：
- `max = -1.2` 被精确还原（qs=0），因为公式就是为它设计的。
- 反方向（如 0.5、-0.8）有 0.05 量化误差，这是 4-bit 离散化的代价。
- 若改用更大的 block（如 32 个权重），d 会被全局 amax 拉得更大，小权重误差会更明显——这正是 K 系列「子块各自有 scale」要解决的问题。

绝大多数量化格式都是「block 内共享 scale + 定点近似」的变体，差异在 scale 怎么选、要不要 min 偏差、scale 本身怎么存。

## 4. K 系列（super-block）结构

### 4.1 设计动机

Q4_0 的问题是：32 个权重共享一个 scale。如果这 32 个里有一个特别大、其他都小，scale 被那个大的拉走，小的就只剩 1~2 个有效 bit。

K 系列的解法：**两级 scale**。
- 外层「超块」(256 权重) 存一个超块 scale `d`（f16）。
- 内层把 256 分成 8 个子块（每个 32 权重），每个子块存一个 6-bit 子 scale `sc` 和 6-bit 子 min `m`。
- 反量化时实际 scale = `d * sc`，实际 min = `dmin * m`——子 scale 是相对超块 scale 的「比例」，用 6 bit 就够。

这样既保留了 32-权重的细粒度 scale，又把 scale 的存储成本摊薄到 256 权重级别。

### 4.2 block_q4_K 实际字段（ggml-common.h:313-327）

```c
// 4-bit quantization
// 8 blocks of 32 elements each
// weight is represented as x = a * q + b
// Effectively 4.5 bits per weight
typedef struct {
    GGML_EXTENSION union {
        struct {
            ggml_half d;    // super-block scale for quantized scales
            ggml_half dmin; // super-block scale for quantized mins
        } GGML_COMMON_AGGR_S;
        ggml_half2 dm;
    } GGML_COMMON_AGGR_U;
    uint8_t scales[K_SCALE_SIZE]; // scales and mins, quantized with 6 bits  (K_SCALE_SIZE=12, ggml-common.h:90)
    uint8_t qs[QK_K/2];           // 4-bit quants (256/2 = 128 字节)
} block_q4_K;
```

字段说明（全部从头文件抄过来，没有编造）：
- `d` (ggml_half, 2 字节)：超块 scale，是子块 scale 的「单位」。
- `dmin` (ggml_half, 2 字节)：超块 min scale，是子块 min 的「单位」。
- `scales[12]`：8 个子块的 scale + 8 个子块的 min，每个 6 bit，共 `8*6 + 8*6 = 96 bit = 12 字节`。打包方式见 `get_scale_min_k4`（ggml-quants.c:822-829）。
- `qs[128]`：256 个 4-bit 量化值，每字节打包 2 个。

**bpw 验证**：
```
block 字节 = 2(d) + 2(dmin) + 12(scales) + 128(qs) = 144 字节 = 1152 bit
bpw = 1152 / 256 = 4.5
```

和 Q4_0 一样是 4.5 bpw！但 Q4_K 用同样的位预算做到了：
- 每 32 权重一个独立 scale（而非 Q4_0 每 32 一个 16-bit scale）
- 每 32 权重一个独立 min（Q4_0 完全没有）
- scale 通过 `make_qkx2_quants` 加权优化选择（Q4_0 只用 amax）

这就是 Q4_K 比 Q4_0 在困惑度上明显更好的原因——同位预算，更聪明的分配。

### 4.3 6-bit scale 怎么存（ggml-quants.c:822-829）

```c
static inline void get_scale_min_k4(int j, const uint8_t * q, uint8_t * d, uint8_t * m) {
    if (j < 4) {
        *d = q[j] & 63; *m = q[j + 4] & 63;
    } else {
        *d = (q[j+4] & 0xF) | ((q[j-4] >> 6) << 4);
        *m = (q[j+4] >>  4) | ((q[j-0] >> 6) << 4);
    }
}
```

8 个子块的 scale + min 共 16 个 6-bit 值 = 96 bit。打包到 12 字节里需要点技巧：前 4 个子块的 scale/min 直接放 `scales[0..7]` 的低 6 位（高 2 位空着），后 4 个子块的 scale/min 拆成「低 4 位 + 高 2 位」，高 2 位塞进前 4 个字节的高 2 位。读出来时 `get_scale_min_k4` 还原。这种紧凑打包是 K 系列算法的「细节税费」。

### 4.4 量化流程（quantize_row_q4_K_ref, ggml-quants.c:1399-1469）

```
对每个 256-权重的超块：
  1. 对 8 个子块各自调用 make_qkx2_quants，求最优 scale 和 min（:1418）
     - make_qkx2_quants 用加权误差最小化搜索，不是简单 amax
     - 权重 weights[l] = av_x + |x[l]|，让大权重误差计权更高
  2. 找 8 个子块里的 max_scale 和 max_min（:1420-1426）
  3. inv_scale = 63 / max_scale（:1429）—— 把 max_scale 量化到 6-bit 满量程 63
  4. 量化每个子块 scale: ls = round(inv_scale * scales[j]), clamp [0,63]（:1432-1435）
  5. 存超块 d = max_scale / 63（:1445），反量化时实际 scale = d * ls
  6. 用「已量化的 scale」重新量化每个权重（:1454-1458）：
       l = round((x + dm) / d)，dm = dmin * m
       clamp [0, 15]
  7. 把 256 个 4-bit 值打包到 qs[128]（:1461-1465）
```

反量化（:1471-1493）就是 `x = d * sc * (q & 0xF) - dmin * m`。

注意第 6 步——量化用的不是原始 scale，而是「量化后的 scale」。这是必要的：反量化时只能拿到量化后的 scale，权重量化必须基于同样的 scale 才能无损还原。

### 4.5 为什么 K 系列误差更小

把上面几点合起来：
1. **子块粒度**：32 权重一个 scale，不是 256，局部幅度变化能跟上。
2. **非对称**：有 min 偏差，能把零点对齐，比 Q4_0 的对称式更省有效位。
3. **加权优化**：`make_qkx2_quants` 不是 amax，而是最小化 `sum(weights[l] * (x[l] - dequant)^2)`，大权重的精度优先保障。
4. **scale 自身量化**：6-bit 子 scale + 16-bit 超块 scale，等价于用 ~6.5 bit 存每个 32-子块的 scale（vs Q4_0 的 16 bit），省下来的位都给了 min 偏差。

## 5. imatrix（重要性矩阵）

### 5.1 原理

Q4_K 的 `make_qkx2_quants` 用 `weights[l] = av_x + |x[l]|` 作权重——这是个**静态**启发式：大权重要求精度高。但这不一定是真正重要的权重。

真正影响模型输出的是「被大激活乘上的权重」。一行权重如果在推理时常常被大激活相乘，它的量化误差会被放大；如果激活常接近 0，它的误差就被抑制。

imatrix（importance matrix）就是校准集上每行权重的「激活幅度统计」：跑一批校准文本，前向时累加每行 `|activation|^2`，归一化后得到每行的「重要性」。量化时把这个重要性当 `weights[l]` 喂给 `make_qkx2_quants`——重要的行用更精细的 scale，不重要的行可以粗糙一点。

### 5.2 为什么对 K 系列 / 低比特特别关键

- **K 系列**：子块 scale 是加权优化选出来的，权重的质量直接决定优化方向。没有 imatrix 时用 `av_x + |x|` 是「盲猜」重要性；有 imatrix 后用真实激活幅度，scale 选择立刻更贴合推理场景。
- **低比特（IQ2/IQ3）**：2~3 bit 时每个量化值要管 4~8 个原始值，scale 错一点整个子块全歪。imatrix 几乎是必需品——`tensor_requires_imatrix`（llama-quant.cpp:767-786）强制要求 IQ2_XXS/XS/S、IQ3_XXS、IQ1_M/S 这些低比特格式必须提供 imatrix，否则量化会失败。

imatrix 是 llama.cpp i-quant（importance-aware quantization）的核心，能让 Q4_K 在 PPL 上再降一截，让 IQ2_XXS 这种「极限压缩」变得可用。

## 6. 编排流程（llama-quant.cpp）

### 6.1 类型选择 llama_tensor_get_type（:661-703）

逐 tensor 决定量化类型，优先级（高到低）：

1. **不允许量化的张量**（`tensor_allows_quantization` 返回 false，:662）：保持原类型。包括 norm 层（RMSNorm 的权重幅度极敏感）、某些 1D 张量等。
2. **用户显式指定**（:665-670）：`--token-embedding-type` / `--output-tensor-type` 直接覆盖。
3. **正则 override**（:678-691）：`--tensor-type` 参数按名字匹配，命中则用指定类型，标记 `manual=true`。
4. **混合策略** `llama_tensor_get_type_impl`（:695，函数体在 :411）：未手动指定时，按 ftype + 张量类别 + 层号自动选型。
5. **形状回退** `tensor_type_fallback`（:699）：上面选出的类型若与张量形状不兼容，回退到兼容类型。

### 6.2 为什么 output / embedding 常留高精度

`llama_tensor_get_type_impl` 对 `OUTPUT` 类张量（和 tied embedding）的默认处理（:439-460）：
- 用户显式指定就用指定的。
- 否则默认 **Q6_K**（:458），除非已经是 Q8_0。
- 极低比特 ftype（IQ2/IQ1）时退到 Q5_K（:452-456）。

原因：output 投影层（`output.weight`，shape `[vocab, hidden]`）直接决定下一个 token 的概率分布，一点点量化误差会被 softmax 放大成排序错误。embedding 矩阵同理（tied 时就是同一个张量）。这两层留高精度，其它层用低比特，是性价比最高的分配。

`use_more_bits` lambda（:417-419）还体现了一个经验：**首尾层和每隔 3 层的特殊层用更多 bit**。`i_layer < n/8 || i_layer >= 7n/8 || (i-n/8)%3 == 2` 时返回 true，给这些层用更精细的类型。理由是首尾层对最终输出影响最大，中间某些层（残差关键节点）也敏感。

### 6.3 fallback 的场景（tensor_type_fallback, :362-408）

只有一种情况会触发：**张量第一维 ncols 不是 block size 的整数倍**。例如某层 hidden=3200，3200 % 256 = 128 ≠ 0，无法用 Q4_K（block=256）。回退规则（:373-393）：

| 目标类型 | 回退到 |
|---|---|
| Q2_K / Q3_K / TQ1_0 / TQ2_0 | Q4_0 |
| Q4_K | Q5_0 |
| Q5_K | Q5_1 |
| Q6_K | Q8_0 |
| IQ1/IQ2/IQ3/IQ4_XS | IQ4_NL |

若回退后的类型仍不兼容（极少见，通常是 ncols 不是 32 的倍数），最终退到 F16（:402）。

### 6.4 多线程量化 llama_tensor_quantize_impl（:709-761）

- **单线程**（nthread < 2）：直接 `ggml_quantize_chunk` 量化整个张量，`ggml_validate_row_data` 校验（:710-717）。
- **多线程**：按 `chunk_size` 切分行，worker 用 `mutex + counter` 抢任务（:727-735），各自量化自己的 chunk 并校验（:737-748）。任何 chunk 校验失败就把 `valid=false`，最后抛异常。
- **imatrix 透传**：作为 `quant_weights` 参数传给 `ggml_quantize_chunk`，最终被 `make_qkx2_quants` 等用上（:712, :738）。

校验（`ggml_validate_row_data`）会检查 block 对齐、scale 是否非 NaN、量化值是否在合法范围等，防止单线程跑出脏数据被默默写入 GGUF。

## 7. 图视角小结（和 01/03 呼应）

- 卷积/FFN 的权重在**加载时**就从 GGUF 读成量化块，matmul 时「整块读取 + 定点乘加」，正是 SIMD/GPU 喜欢的形态。
- 量化类型是 per-tensor 存于 GGUF 元数据，`f16 -> q4_0` 等转换就是跑一遍 `llama_tensor_quantize_impl`。
- 量化对「精度 vs 速度」的取舍，是 llama.cpp 相对其他推理框架最核心的差异化能力之一。
